### 重要な決定と理由

- **版は v2.4.0。** rc 系列は `2.3.1-rc*` の名で進んでいたが、`v2.3.0` 以降に feat が 7 件、rc4 の後にも
  2 件（時刻コピー・明色配色）入っている。patch で出すと「2.3.0 → 2.3.1 は修正のみ」と誤読される。
- **main へマージしてからタグ。** `v2.3.0` が main 上にある先例に合わせた。rc はブランチ上でタグする運用。
- **タグを 2 回付け直した（push 前）。** 最初のタグはビルドが通らない、2 回目は成果物名が旧名のままだった。
  未 push なら付け直しの害は無く、「タグ＝再現できる状態」を保つ方を優先した。
- **push 後は付け直さない。** タグが docs 3 件を含まない形になったが、CI が既に消費したタグを force push する
  方が害が大きい。差分は README と PAD 図だけでバイナリに影響しない。
- **updater の修正を改名と同じコミットに入れた。** 改名で `Chaptr-*-Intel.dmg` と `-AppleSilicon.dmg` が
  並ぶことが確定するので、アーキテクチャを見ない選択は実害になる。改名と不可分と判断。
- **arm64 機は Intel 版へフォールバックするが、逆はしない。** Rosetta で動く方向だけ許す。

### 調べて分かった外部仕様

- **PyInstaller の収集漏れは `build/<name>/Analysis-00.toc` で確認できる。** 警告ファイル
  `build/<name>/warn-<name>.txt` は偽陽性（numpy の遅延属性など）が大量に混じるので、
  実際に何が入ったかは toc を見る方が速い。
  ```bash
  python3 -c "
  import re,pathlib
  t=pathlib.Path('build/chaptr/Analysis-00.toc').read_text(errors='ignore')
  core=sorted({m for m in re.findall(r\"'(numpy[._a-zA-Z0-9]*)'\",t) if m.startswith('numpy._core')})
  print(len(core), any('_exceptions' in m for m in core))"
  ```
- **numpy は ImportError を自分の言葉に置き換えて出す。** 実際は
  `No module named 'numpy._core._exceptions'` なのに、表に出るのは
  `Error importing numpy: you should not try to import numpy from its source directory` で、
  原因（収集漏れ）がメッセージから読めない。トレースの上の方に本当の例外が残っている。
- **stdlib の `xml` を excludes に入れると `pkg_resources` が落ちる。** `pkg_resources/__init__.py` →
  `plistlib` → `xml`。`ModuleNotFoundError: No module named 'xml'` は PyInstaller のランタイムフック
  `pyi_rth_pkgres` の中で出るので、アプリ側のコードを探しても見つからない。
- **`gh run watch --exit-status` の終了コードは完了を意味しない。** 今回
  `failed to get jobs: HTTP 502: Server Error` を出して **exit code 0** で戻った。実際の run は
  `queued` のままだった。完了判定は `gh run view <id> --json status,conclusion` を自分で回す。
- `release.yml` はタグ push で発火し、Intel（`macos-15`）/ arm64（`macos-latest`）/ Windows の 3 本を
  ビルドして `softprops/action-gh-release@v1` で添付する。添付は `*.dmg` / `*.exe` のグロブなので
  成果物名の変更は公開ジョブに影響しない。prerelease はタグ名にハイフンが含まれるかで決まる。
- `updater.py` は拡張子だけでアセットを選んでいた（名前は見ない）。改名の影響は無かったが、
  **成果物が 2 アーキテクチャに増えた時点で壊れていた**。

### 検討して採らなかった選択肢と理由

- **v2.3.1 として出す** — rc 系列の命名意図は継げるが、rc4 の後に入った feat 2 件が patch 扱いになる。
- **ブランチのままタグする** — マージの判断を後回しにできるが、正式版が main に無い状態が続く。
- **push 後にタグを付け直して docs 3 件を含める** — CI が消費済みのタグを force push することになる。
  バイナリに影響しない差分のために取る手ではない。
- **`collect_submodules('numpy')` を丸ごと入れる** — `numpy.testing` 等 63 個が excludes の `unittest` と
  衝突する。`testing` / `f2py` / `distutils` を除いて入れた。
- **`git worktree` で theming 前のコミットを検証する** — 権限で拒否されたため、コードを読んで
  `QFileSystemModel` の非同期性から原因を特定する方に切り替えた（結果的にこちらが速かった）。

### ハマった点・エラーと回避策

- **ビルドは通るのに起動しない（1 回目）**
  ```
  ImportError: Error importing numpy: you should not try to import numpy from
          its source directory; please exit the numpy source tree, and relaunch
          your python interpreter from there.
  Original error was: No module named 'numpy._core._exceptions'
  ```
  → `Analysis-00.toc` で収集漏れを確認し `collect_submodules('numpy')` を追加。
- **起動しない（2 回目）**
  ```
  ModuleNotFoundError: No module named 'xml'
  [PYI-86854:ERROR] Failed to execute script 'pyi_rth_pkgres' due to unhandled exception: No module named 'xml'
  ```
  → spec の `excludes` から `'xml'` を外す。numpy 収集で `pkg_resources` が入ったことが引き金。
- **一括置換がヘルパー自身を書き換えた。** `app.processEvents()` を 6 箇所置換したが、意図していたのは
  テスト 4 箇所で、残り 2 箇所は**新しく足したヘルパーの中**だった。結果 `NameError: name 'dlg' is not defined`
  で 4 件が確実に落ちる状態になった。置換前に「意図した件数」を数えていれば 6≠4 で気づけた。
- **テストが毎回違うケースで落ちる。** `QFileSystemModel` は `setRootPath()` を別スレッドで走査するため、
  `app.processEvents()` 1 回では空のモデルを検査していた。走査完了を待つ `_wait_loaded()` を置いた。
- **`gh run watch` が嘘の完了を返した。** 上記「調べて分かった外部仕様」参照。危うく「リリース成功」と
  報告しかけた（`gh release view` が `release not found` を返して気づいた）。
- `rm -rf build dist` を含むコマンドが権限で拒否された → 破壊的操作を外して実行。
- `git worktree add` も拒否された。
