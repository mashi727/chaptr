# 上流設計の教科書 — コードを書き始める前に決めること

> **このコースの背骨。** 主題は「Chaptrの作り方」ではなく、**上流設計（upstream design）＝実装に入る前の意思決定**の体系である。
> Chaptrは題材（case study）にすぎない。うまく決めた所・決め損ねた所の**両方**を証拠として使い、
> 「先に決めておけば、この代償（2回のリブランド／15コミットの配布地獄／重複タイムスタンプのバグ）は避けられた」を実データで示す。
>
> 年表としての記録は `course/01-開発ストーリー.md` に置いた。00（本書）は**そこから抽出した原理**を扱う。

---

## 0. なぜ「上流設計」の教材が要るのか

世に出ている開発教材のほとんどは **how to build（作り方）** を教える。
「このライブラリでこう書く」「この手順でデプロイ」——手を動かせば動くものはできる。

だが実際のプロジェクトが破綻するのは、たいてい**コードの書き方ではなく、書き始める前の意思決定を怠った所**だ。

Chaptrの履歴がそれを証明している：

| 症状（実際に起きたこと） | 根本原因（＝決め損ねた上流の意思決定） |
|---|---|
| リポジトリ名を2回改名（`rehearsal-workflow`→`media-scribe-workflow`→`chaptr`） | **名前とアイデンティティ**を後回しにした |
| 配布に15コミットを費やす（Nuitka移行・ffmpeg同梱・OS別クッキー…） | **配布・運用制約**を実装後に考え始めた |
| 除外ハッチングが出ないバグ（区間幅0） | 「除外区間とは何か」という**データの契約**が曖昧だった |
| リブランドでアイコンが消失 | **中核資産の管理方針**（何をgit追跡するか）が未定義だった |
| 7分で9コミットの大量ランディング | **分解方針**が実装中に後付けになった |

これらは「腕が悪い」から起きたのではない。**着手前に言語化していれば、そもそも発生しなかった**類の問題だ。
本書は、その「着手前に言語化すべきこと」を10領域に整理し、**どう考え、どう設計思想に落とすか**を教える。

## 1. 中心にある1枚：上流設計キャンバス

上流設計は「たくさん考える」ことではない。**1枚の紙に、後で変えると高くつく決定だけを書き切る**ことだ。
本コースの成果物は、この **上流設計キャンバス** を自分のプロジェクトで埋められるようになること。

```
┌─────────────────────────────────────────────────────────────┐
│  上流設計キャンバス（着手前に埋める1枚）                       │
├───────────────┬─────────────────────────────────────────────┤
│ ① 課題         │ 誰の・どんな痛みを・どの頻度で                 │
│ ② 成功条件     │ 何ができたら「解決」と言えるか（Done の定義）   │
│ ③ スコープ境界 │ やる / やらない / 将来やるかも                 │
│ ④ 中核データと │ 一番安定させたいデータ構造・ファイル形式・       │
│    契約        │ 不変条件（invariant）                        │
│ ⑤ 分解方針     │ 単一目的の単位は何か／層の分け方／可変・不変の境界│
│ ⑥ 配布・運用   │ 誰が・どのOSで・どう入手・依存はどう同梱         │
│ ⑦ 技術選定     │ 何を選ぶか／「乗り換える条件」もセットで         │
│ ⑧ 可逆性マップ │ 片道ドア（慎重に）／両開きドア（即決してよい）    │
│ ⑨ AI協働設計   │ CLAUDE.md方針／自分が握る判断／ガードレール      │
│ ⑩ 名前と識別   │ 変更コストの高い名前を先に固定                 │
└───────────────┴─────────────────────────────────────────────┘
```

**重要な性質：**
- キャンバスは**全部を先に決める**ためのものではない。**「後で変えると高くつくもの」だけ**を先に固定し、それ以外は意図的に空欄のまま走り出す（⑧が空欄の可否を判定する）。
- これは要件定義書でも設計書でもない。**判断の根拠を1枚に外在化**する道具。Claude Codeに渡す `CLAUDE.md` の骨格そのものになる（→ ⑨）。

以降、10領域を1つずつ「何を決めるか／なぜ着手前か／どう考えるか／Chaptrの実際 vs 理想／設計思想への落とし込み」で解説する。

## 2. 十の意思決定領域

各領域は同じ型で書く：

- **決めること** — キャンバスに書く一文
- **なぜ着手前か** — 後回しにした時のコスト（＝Chaptrで実際に払った代償）
- **考え方** — 決めるための問い・フレーム
- **実際 vs 理想** — Chaptrはどうだったか／上流で決めていたら
- **落とし込み** — 設計思想（CLAUDE.md）への書き方

---

### ① 課題 — 「誰の・どんな痛みを・どの頻度で」

**決めること：** 解決する痛みを一文で。理想は自分が当事者（dogfooding）。

**なぜ着手前か：** 課題が曖昧だと、④以降すべてがぶれる。「あったら便利」で作り始めた機能は、優先順位を付けられず肥大化する。

**考え方（問い）：**
- この痛みは**誰の**ものか。自分か、想像上のユーザーか（想像上なら要注意）。
- **頻度 × 一回あたりの苦痛** はどれくらいか。自動化する価値があるか。
- 痛みを**一文**で言えるか。言えないなら課題がまだ解けていない。

**実際 vs 理想（Chaptr）：**
- ✅ ここはChaptrの数少ない「最初から正しかった」点。出発点は自分の実需要——**リハーサル動画から、指揮者の指示を字幕化してレポートPDFにする**。当事者だから、後半の日本語濁点バグやインターレース問題という「使わないと出ない痛み」まで拾えた（＝ドッグフーディングの配当）。

**落とし込み：** `CLAUDE.md` の冒頭「プロジェクト概要」。Chaptrは実際にこう書いている——
> リハーサル動画から字幕（SRT）を取得するシンプルな配管ツール群。

一文で痛みと手段が言えている。これが良い課題定義。

---

### ② 成功条件 — 「何ができたら解決か」

**決めること：** Done の定義。ここまでできたら v1 完成、と言える線。

**なぜ着手前か：** 終わりを決めないと、永遠に「あと1機能」を足し続ける。MVPの範囲が決まらない。

**考え方：**
- 「解決した状態」を**観測可能な形**で書く（例：「13:30〜17:00の生動画から、章付きMP4と字幕SRTが1本出る」）。
- v1 と v2 の線を引く。**v1に入れないもの**を明記する方が重要。

**実際 vs 理想（Chaptr）：**
- △ Chaptrは成功条件を早く言語化しなかった。結果、MVP（12/31）は動いたが、その後「配布」「字幕表示」「回転」と、どこまでがv1か曖昧なまま機能が積み上がった。
- 理想：「章付き動画＋SRTが1本出る」をv1のDoneと最初に宣言していれば、配布(Section4-5)は「v1のDoneに含むか？」を意図的に判断できた（＝含めるなら最初から設計、含めないなら後回し）。

**落とし込み：** `CLAUDE.md` の「実装済み/未実装タスク」。ChaptrのCLAUDE.mdには実際にこのチェックリストがある。これはDoneの定義の代替として機能している。**着手前に書き、進捗で消し込む**のが理想。

---

### ③ スコープ境界 — 「やる / やらない / 将来やるかも」

**決めること：** In / Out / Later の3分類。特に **Out を書く**。

**なぜ着手前か：** スコープの膨張は、リポジトリ構成・依存・配布すべてに波及する。**境界を後で引き直す = リポジトリを割り直す**ことになり、これは最も高い代償の一つ。

**考え方：**
- 機能を In / Out / Later に振る。**Out に理由を添える**（「なぜやらないか」が思想になる）。
- 「階層」で考える：**誰でも使える / 興味があれば / 本気の人向け**、と利用者の本気度で層を分ける。層をまたぐ機能は疑う。

**実際 vs 理想（Chaptr）：**
- ❌ ここがChaptr最大の教訓。当初は **CLI配管ツール ＋ LaTeXレポート ＋ GUI** を1つの `media-scribe-workflow` に全部入れた monorepo だった。
- スコープ境界を決めていなかったため、GUIが育つにつれ「これは別物では？」と気づき、**5ヶ月後に `chaptr` としてGUIを切り出すリブランド（`01ef476`）**を強いられた。100ファイル超のリネーム、READMEを276行削り、その過程でアイコン移行漏れバグまで生んだ。
- 理想：着手前に「GUIとCLIは別の利用者・別の配布形態」と見抜き、**最初から別リポジトリ**にしていれば、リブランドもアイコン消失も起きなかった。境界は**コードではなくリポジトリで割る**のが、この規模の正解だった。

**落とし込み：** ChaptrのCLAUDE.mdは今では良い見本になっている——
> コア: 動画/音声 → SRT取得 ／ 参考として提供: プロンプト例・環境構築ガイド

そして「階層」節で誰でも/興味があれば/本気の人向けを明示。**これを最初に書けていれば**、というのがこの領域の学び。

---

### ④ 中核データと契約 — 「一番安定させるもの」

**決めること：** アプリの背骨になるデータ構造・ファイル形式・**不変条件（invariant）**。

**なぜ着手前か：** データの形は、UI・エクスポート・保存・テスト、全経路が依存する。**契約が曖昧だと、経路ごとに解釈がずれてバグになる**。

**考え方：**
- 「一番変えたくないデータは何か」を先に決める。ChaptrならチャプターのリストとVCEプロジェクト形式。
- **不変条件を書く**：「チャプターは時刻昇順」「同一時刻は許すのか？」「先頭は必ず0:00:00か？」。ここを詰めるほど後のバグが減る。
- 契約は**純粋関数**として1箇所に閉じ込める（single source of truth）。UIやworkerに散らさない。

**実際 vs 理想（Chaptr）：**
- ❌ 「除外区間（`--`で始まる章の範囲）」の契約が曖昧だった。**「同一時刻の章が複数あったらどうなるか」を決めていなかった**。
- 実データで先頭 `0:00:00 --捨て` と末尾 `0:00:00 アンコール` が衝突し、区間が `0→0`（幅0）になって斜線が1pxも描かれない——これが `ea120d3` のバグ。しかも計算ロジックが**波形・エクスポート・テストに3重コピー**されていて、テストが本番を守れていなかった。
- 理想：着手前に不変条件「章は時刻昇順・同一時刻は起こりうる・区間は厳密に大きい次の時刻まで」を宣言し、`compute_excluded_regions()` という**純粋関数を最初から1本**用意していれば、バグも「テストが本番をコピー」問題も発生しなかった。実際の修正は**まさにこの形に作り直す**ことだった（＝後からたどり着いた正解を、上流で先取りする）。

**落とし込み：** CLAUDE.mdの「決定事項」や設計仕様に、**データの不変条件を箇条書き**で書く。「この関数がその唯一の実装」と場所も固定する。

---

### ⑤ 分解方針 — 「単一目的の単位と層」

**決めること：** 何を単一目的の部品にするか。層（状態／UI仲介／重い処理）の分け方。可変と不変の境界。

**なぜ着手前か：** 分解を後付けにすると、1ファイルが数千行に膨れてから泣きながら割ることになる。

**考え方：**
- **「Gitの陶器と配管」**（Chaptrの明文化された思想）：単一目的のツールを組み合わせる。まず「配管（低レベル単機能）」と「陶器（人向けの入口）」を分ける。
- GUIなら層で分ける：**managers（状態を持つ）/ controllers（UIと状態を仲介）/ workers（重い・非同期処理）**。
- **可変（UIの見た目）と不変（データモデル）**の境界を引く。不変側をimmutableにすると安全。

**実際 vs 理想（Chaptr）：**
- △ 思想（配管とporcelain）は最初からCLAUDE.mdにあった。だがGUI内部の層分けは**後から**。`MainWorkspace` が7404行に膨れてから managers→controllers/workers に割った（フェーズ2〜3）。
- しかもその大リファクタは**7分で9コミットの一括ランディング**として着地し、「なぜこう割ったか」の物語が潰れた。
- 理想：着手前に「状態・UI仲介・重処理の3層」と「immutableなデータモデルを中核に」を宣言していれば、MainWorkspaceは最初から薄く保て、リファクタは小さな連続コミットで済んだ。

**落とし込み：** CLAUDE.mdの「ディレクトリ構成（予定）」。Chaptrは実際にツリーを**予定として**先に描いている。これは分解方針の可視化として正しい。GUI内部の層も同じ粒度で先に描くべきだった。

---

### ⑥ 配布・運用制約 — 「誰が・どのOSで・どう入手」

**決めること：** ターゲットOS、入手経路、依存の同梱方針。**これは制約であって後付けの工程ではない。**

**なぜ着手前か：** 配布はアーキテクチャを縛る。「ffmpegに依存する」「OSごとにブラウザのクッキー取得が違う」「ワンファイルEXEにしたい」——これらは**実装方針を規定する制約**であり、後から足すと総取っ替えになる。

**考え方：**
- 「誰が」「どのOSで」「どうやって入手し」「起動するまでに何を要求するか（別途ffmpegを入れさせるのか？）」を先に書く。
- 依存の**同梱方針**を決める：外部バイナリ（ffmpeg/yt-dlp）はバンドルするのか、要求するのか。
- 配布形態（pip / DMG / EXE）を先に決めると、パッケージャ選定（PyInstaller / Nuitka）が導ける。

**実際 vs 理想（Chaptr）：**
- ❌ 配布を実装後に考え始めた結果、フェーズ2で**15コミットの配布地獄**：macOSデュアルアーキ、ffmpeg/ffprobe同梱、Windowsのコンソールちらつき→onedir→Nuitka移行→メモリ不足→yt-dlp外部exe分離→CIの対話プロンプト詰まり…と、1つ直すと次が出る連鎖。
- 理想：着手前に「配布先＝macOS(AppleSilicon/Intel)とWindows、入手＝スタンドアロン配布、ffmpegは同梱、対話ダウンロードはCIで詰まる」まで見通していれば、**最初からNuitka前提・ffmpeg同梱前提**で組め、この連鎖の大半は設計時に吸収できた。
- ※ただし「全部を先読みするのは不可能」も真実。だからこそキャンバス⑥は「完璧な予言」ではなく「**この制約は実装を縛る、と自覚しておく**」ためにある。地獄を消すのではなく、地獄を**予期された作業**に変えるのが目的。

**落とし込み：** CLAUDE.mdやREADMEに配布マトリクスを書く。Chaptrは今ではREADMEに「プラットフォーム／パッケージ形式／エンコード」の表を持つ。着手前版として書けるとよい。

---

### ⑦ 技術選定 — 「選択と、乗り換える条件」

**決めること：** 主要技術の選定。そして**それぞれ「どうなったら乗り換えるか」の条件**をセットで。

**なぜ着手前か：** 選定自体より、「いつ見切るか」を決めておくことが後の消耗を防ぐ。条件を決めていないと、劣勢なツールに回避策を積み続ける。

**考え方（乗り換えを決める3つの問い）：**
1. 今のツールで、あと**何回**回避策を積むことになりそうか？
2. 乗り換え先は、その問題を**構造的に**解決するか（対症療法でないか）？
3. 乗り換えの**コスト（CI再構築など）**は許容できるか？

**実際 vs 理想（Chaptr）：**
- Chaptrは実際にこの判断をした：WindowsでPyInstallerのコンソール問題に回避策（onefile→onedir）を積んだ後、「これは構造的に解決しない」と見て **Nuitkaへ乗り換え（`f62a81c`）**。しかもmacOSはPyInstallerのまま——**全部を一気に乗り換えない**のも良い判断だった。
- 学び：選定は「最初に正解を選ぶ」ことではなく、**乗り換え条件を先に決めておき、条件が満たされたら迷わず動く**こと。

**落とし込み：** CLAUDE.mdの「決定事項」に「技術Xを採用。ただしYになったらZへ」と条件付きで書く。

---

### ⑧ 可逆性マップ — 「片道ドアと両開きドア」

**決めること：** どの決定が**取り消しに高コスト（片道ドア）**で、どれが**すぐ戻せる（両開きドア）**か。

**なぜ着手前か：** これは**メタ意思決定**。①〜⑩のどれを慎重に決め、どれを即決して走り出してよいかを仕分ける。上流設計を「全部を悩む」から救う。

**考え方：**
- **片道ドア**（慎重に、着手前に決める）：データ形式・リポジトリ名/構成・配布チャネル・公開API/ファイル契約。一度公開すると互換性の鎖ができる。
- **両開きドア**（即決OK、後で直す）：UIレイアウト・色・キーボードショートカット・ログの文言。
- 迷ったら「これを3ヶ月後に変えると何がドミノ倒しになるか」を問う。倒れる数が多いほど片道ドア。

**実際 vs 理想（Chaptr）：**
- ❌ Chaptrは**片道ドアを両開きだと誤認**した典型。リポジトリ名（`rehearsal`→`media-scribe`→`chaptr`）とパッケージ名を軽く考え、2回改名。パッケージ名の変更は import 文・エントリポイント・specファイル・パス文字列・CI設定すべてに波及する片道ドアだった。
- ✅ 一方、テーマ色やアイコンデザイン（両開きドア）は気軽に何度も変えた——これは正しい。TokyoNightアイコンへの変更などは軽い決定でよい。

**落とし込み：** キャンバス⑧に2列で列挙。片道ドア側だけCLAUDE.mdの「決定事項」に格上げして固定する。

---

### ⑨ AI協働設計 — 「Claude Codeとどう組むか」

**決めること：** `CLAUDE.md` に何を書くか。自分が握る判断とClaudeに委ねる作業の線。ガードレール（記録・ブランチ規律・確認の作法）。

**なぜ着手前か：** AIとの協働は**それ自体が設計対象**。CLAUDE.mdは実装物ではなく**設計意図の外在化**であり、上流で書くほど全セッションの質が上がる。

**考え方：**
- **CLAUDE.mdは設計思想の置き場**：概要・スコープ・ディレクトリ・決定事項＝キャンバス①③⑤⑦⑧の写像。
- **人間が握る判断／AIに委ねる作業**を分ける：課題定義・スコープ境界・片道ドア＝人間。定型実装・調査・リファクタ・テスト作成＝AIに委ねてよい。
- **ガードレール**：作業ブランチで作業（デフォルトブランチ直コミット禁止）、`worklog` で文脈を次セッションへ引き継ぐ、「**まずデータの値を見る**」を原則にする。

**実際 vs 理想（Chaptr）：**
- ✅ CLAUDE.mdは最初から存在し、思想・スコープ・決定事項を書いていた——これがClaudeを賢く動かした土台。
- △ ガードレール（worklog）は**後半（5月）に習慣化**。もっと早く始めていれば、序盤の配布地獄の判断過程も記録として残り、この教材の裏付けも厚くなった。
- 実例の質：5/27のセッションでClaudeが `AskUserQuestion` で切り分けようとした時、**ユーザーが質問に答えず実データを渡した**。これは「AIに委ねる/人間が握る」の好例——切り分けの前提となる生データの提示は人間の仕事。

**落とし込み：** CLAUDE.md本体が成果物。加えて「ユーザーからの指示・好み」をworklogに残し、セッションを越えて思想を保つ。

### ⑩ 名前とアイデンティティ — 「安いうちに、しかし後戻りは高い」

**決めること：** プロダクト名・パッケージ名・エントリポイント名。**変更コストが高いものを先に固定する。**

**なぜ着手前か：** 名前は片道ドア（⑧）の代表。公開後の改名は、パッケージ名・import・パス・CI・配布物・ユーザーのブックマークまで巻き込む。

**考え方：**
- 名前は「決めるのは安いが、変えるのは高い」。だから**完璧を狙わず、しかし早めに固定**する。
- **内部名と外部名を分離**する手もある：内部パッケージ名を汎用に保ち、表示名だけ後で変える。そうすればブランド変更が片道ドアにならない。
- 命名の射程を先に定義（このリポジトリは「GUIだけ」なのか「ワークフロー全体」なのか）＝③スコープと直結。

**実際 vs 理想（Chaptr）：**
- ❌ `rehearsal-workflow`（用途に寄りすぎ）→ `media-scribe-workflow`（まだ広すぎ）→ `chaptr`（スコープ確定後にようやく的確）。**名前がスコープの迷いをそのまま反映**していた。
- 理想：③スコープ境界を着手前に固めていれば、名前も一度で `chaptr` に決められた。**名前の揺れは、たいていスコープの揺れの症状**。

**落とし込み：** キャンバス⑩に確定名を書き、⑧の片道ドア側に置く。決めたら `pyproject.toml`・エントリポイント・specに一気に反映し、以後動かさない。

## 3. 上流設計を「設計思想」に落とし込む

キャンバス（10領域）を埋めたら、それを**2つの成果物**に凝縮する。これが「設計思想への落とし込み」の具体。

### (a) CLAUDE.md ＝ 生きた設計思想
キャンバスの写像を、Claudeが毎セッション読む場所に置く：

| キャンバス | CLAUDE.md の節 |
|---|---|
| ① 課題 | プロジェクト概要 |
| ③ スコープ境界 | 設計方針 / スコープ / 階層 |
| ④ 契約・不変条件 | 決定事項 / 設計仕様 |
| ⑤ 分解方針 | ディレクトリ構成（予定） |
| ⑥ 配布制約 | （README配布マトリクス） |
| ⑦⑧ 技術・可逆性 | 決定事項（条件付きで） |
| ② 成功条件 | 実装済み / 未実装タスク |

Chaptrの現行CLAUDE.mdは、**結果的に**この形にかなり近い。本コースの主張は「これを**着手前に**書け」。

### (b) 判断ログ ＝ 思想の更新履歴
決定は変わる。変わったときに「なぜ変えたか」を残す仕組みが `worklog/`。
設計思想は石版ではなく、**判断とその理由の連なり**。worklogは思想のgit historyにあたる。

### 落とし込みの合言葉
> **決定を、コードでなく文章で外在化せよ。**
> コードは How を語るが、上流設計が守りたいのは Why と境界。それはCLAUDE.mdと判断ログにしか書けない。
