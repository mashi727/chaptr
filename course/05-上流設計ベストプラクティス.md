# 上流設計ベストプラクティス（実践プレイブック）

> `course/00-上流設計の教科書` を、**着手前に手を動かせる形**に凝縮した1枚。
> 原則・Do/Don't・アンチパターンを、すべて **Chaptrの実際の証拠**（commit / CHANGELOG / worklog）に紐づけてある。
> コースの持ち帰り資料（ハンドアウト）として、また各章の要点確認として使う。

---

## 0. 大原則（これだけは覚える）

> **決定を、コードでなく文章で外在化せよ。**
> コードはHowを語る。だが上流設計が守るのは **Why と 境界**。それはCLAUDE.mdと判断ログにしか書けない。

3つの下位原則：
1. **全部を先に決めない。** 後で変えると高くつく決定（片道ドア）だけを先に固定する。
2. **名前の揺れは、スコープの揺れの症状。** 迷いは症状であって原因ではない。原因（境界）を先に断つ。
3. **地獄は消せない、が予期はできる。** 配布・移行の揉めごとを「予期された作業」に変えるのが上流設計。

## 1. 着手前チェックリスト（1枚キャンバスの10問）

コードを1行も書く前に、この10問に**一文ずつ**答える。答えられないマスは、まだ設計が済んでいない。

| # | 問い | 答えられないと起きること（Chaptr証拠） |
|---|---|---|
| ① 課題 | 誰の・どんな痛みを・どの頻度で解くか？ | 「あったら便利」で機能が膨張 |
| ② 成功条件 | 何ができたらv1完成か。**v1に入れない**ものは？ | Doneの線が引けず終わらない（②△） |
| ③ スコープ境界 | In/Out/Later。**別リポジトリに割る塊**は？ | monorepo→5ヶ月後に分離・100+改名（`01ef476`） |
| ④ 中核データと契約 | 中核データと**不変条件3つ**は？ | 「同時刻可？」未定義→1pxバグ（`ea120d3`） |
| ⑤ 分解方針 | 単一目的の単位・3層（状態/仲介/重処理）は？ | 7404行→7分9コミットの一括着地 |
| ⑥ 配布・運用制約 | どのOS・入手経路・依存の同梱方針は？ | 配布地獄15コミット |
| ⑦ 技術選定 | 選択と**乗り換え条件**は？ | 劣勢ツールに回避策を積み続ける |
| ⑧ 可逆性 | 片道ドアと両開きドアの仕分けは？ | 名前を両開きと誤認→2回改名 |
| ⑨ AI協働 | 握る判断・委ねる作業・ガードレールは？ | 丸投げで的外れ／記録が残らない |
| ⑩ 名前 | 確定名は？内部名と外部名を分けるか？ | rehearsal→media-scribe→chaptr |

> 埋め方の実物は `course/exercises/上流設計キャンバス-テンプレート.md` と `-Chaptr記入例.md`、1枚絵は `course/upstream-canvas.html`。

## 2. 領域別 Do / Don't

### ③ スコープ境界
- ✅ **Out を理由付きで書く。** 「なぜやらないか」が思想になる。
- ✅ **別の利用者・別の配布形態の塊は、フォルダでなくリポジトリで割る。**
- ❌ 「とりあえず1つのリポジトリに全部」入れて後で考える。
- 📌 証拠：CLI＋LaTeX＋GUIの同居 → GUIを`chaptr`へ分離。README **-207行**、アイコン消失（`bac6ff9`）まで連れてきた。

### ④ 中核データと契約
- ✅ **不変条件を先に書く。** 「同時に起きたら？／空なら？／順序は？」の3つを必ず問う。
- ✅ **契約は純粋関数1本に閉じる**（single source of truth）。UI・worker・テストが同じ1つを呼ぶ。
- ❌ 計算ロジックを表示・保存・テストに**コピー**する（テストが本番を守れなくなる）。
- 📌 証拠：`compute_excluded_regions()` に集約したのが正解だった。**後からたどり着いた形を、上流で先取りする。**

### ⑤ 分解方針
- ✅ **層を着手前に描く**：状態=managers / UI仲介=controllers / 重処理=workers、中核=immutable。
- ❌ 1ファイルが数千行に膨れてから割る。
- 📌 証拠：`MainWorkspace` 7404行 → 一括分割で物語が潰れた。

### ⑥ 配布・運用制約
- ✅ **配布は制約。実装より先に**「OS・入手・依存の同梱」を書く。
- ✅ 配布形態の要件（例：コンソール非表示のワンファイル）から**パッケージャを逆算**する。
- ❌ 機能を作り切ってから「さて配布」。
- 📌 証拠：onedir→Nuitka→yt-dlp分離→CI詰まり→DMG busy の15コミット連鎖。

### ⑦⑧ 技術選定と可逆性
- ✅ 選定に**乗り換え条件をセット**で（「〜が構造的に残るなら〜へ」）。
- ✅ **一気に全部を乗り換えない**（Chaptrは Windowsだけ Nuitka、macOSは据え置き）。
- ✅ **片道ドア**（データ形式・リポジトリ/パッケージ名・公開契約・配布チャネル）だけ慎重に。
- ✅ **両開きドア**（色・レイアウト・ショートカット・ログ文言）は即決して走る。
- ❌ 名前や形式を「後で変えればいい」と両開き扱いする。

### ⑩ 名前
- ✅ 早めに固定。**内部名と外部名を分離**すればブランド変更が片道ドアにならない。
- ❌ スコープが固まる前に名前を決めて、後で3回揺らす。

## 3. アンチパターン集（やりがちな順）

| アンチパターン | 症状 | 処方（本書の該当節） |
|---|---|---|
| **全部を1リポジトリ** | 後でリブランド・分離 | ③ 境界はリポジトリで割る |
| **契約の暗黙化** | 経路ごとに解釈がずれてバグ | ④ 不変条件を先に・純粋関数1本 |
| **テストが本番をコピー** | 本番バグを検知できない | ④ 本番関数を直接検証 |
| **配布を最後に** | パッケージング地獄 | ⑥ 配布は制約として先に |
| **完璧主義で着手できない** | 全マスを埋めようと麻痺 | ⑧ 片道ドアだけ決めて走る |
| **大きすぎるコミット** | 物語が潰れ、後で追えない | 可逆な小コミット（下記4） |
| **決定の理由が消える** | 同じ議論を繰り返す | ⑨ 判断ログ（worklog） |

## 4. コミットと記録の作法（上流設計を"保つ"技術）

上流で決めても、実装中に崩れる。崩さないための運用：

- ✅ **可逆な単位で小さくコミット。** 「1つの決定＝1つのコミット」。
- ❌ 反面教師：7分で9コミットの一括ランディング（`1f54b9e`前後）。動くが、後から「なぜこう分けたか」を追えない。
- ✅ **作業ブランチで作業**し、デフォルトブランチへ直接コミットしない。
- ✅ **判断ログ（worklog）** に「重要な決定と理由」「未完了・宿題」「地雷（デッドコード等）」を残す。次のセッション/自分への引き継ぎになる。判断ログは**設計思想のgit history**。

## 5. キャンバス → CLAUDE.md 写像（落とし込み表）

埋めたキャンバスは、Claudeが毎回読む `CLAUDE.md` に変換して初めて効く。

| キャンバス | CLAUDE.md の節 |
|---|---|
| ① 課題 | プロジェクト概要 |
| ③ スコープ境界 | 設計方針 / スコープ / 階層 |
| ④ 契約・不変条件 | 決定事項 / 設計仕様 |
| ⑤ 分解方針 | ディレクトリ構成（予定） |
| ⑥ 配布制約 | （READMEの配布マトリクス） |
| ⑦⑧ 技術・可逆性 | 決定事項（条件付きで） |
| ② 成功条件 | 実装済み / 未実装タスク |

> Chaptrの現行CLAUDE.mdは結果的にこの形に近い。本コースの主張は一貫：**これを着手前に書け。**

## 6. 15秒セルフレビュー（実装に入る直前に唱える）

1. この決定は**片道ドアか両開きドアか**？（片道なら今ちゃんと決める）
2. 中核データの**不変条件**を1文で言えるか？
3. これは**誰が・どのOSで**動かす？（配布制約を思い出す）
4. いま増やそうとしているのは、**Outに書いたもの**ではないか？
5. この判断の**理由**は、どこかに文章で残っているか？

すべてYesなら書き始めてよい。1つでもNoなら、そのマスに戻る。
