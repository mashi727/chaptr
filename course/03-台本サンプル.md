# 台本 / スライドサンプル（上流設計版）

> `course/02-カリキュラム.md`（13セクション54レク）のうち、**各セクション型の代表7本**を完全台本化したもの。
> このコースは実装ハンズオンではなく**「意思決定の実演」**。台本の型は5ブロック固定：
> **①原則 → ②なぜ着手前か → ③Chaptrの実際＝決め損ね（証拠映写）→ ④理想＝上流で決めていたら（反実仮想）→ ⑤キャンバス演習**。
> 残りのレクチャーはこのフォーマットを複製して埋める。台本は「話す言葉そのまま」で書いてある。
>
> 記法：🎬=画面（git/CHANGELOG/worklog等の**証拠**を映す）、🗣️=ナレーション（そのまま読む）、🖼️=スライド、
> 📋=キャンバス記入例（画面に出す）、✍️=受講者への演習指示、✂️=編集メモ。
>
> ⚠️ このコースの実装画面は**証拠としてのみ**映す。手順の実演（ライブコーディング）はしない。

---

## 台本フォーマット（テンプレート）

各レクチャー冒頭に置くメタ情報：

```
## S{章}.{番} {タイトル}
- 種別: 座学 / ケース分析 / 演習
- 目安: {分}
- キャンバス領域: {①〜⑩ / 全体}
- 証拠（映すもの）: {git show <hash> / CHANGELOG節 / worklog日付}
- このレクのゴール（1文）: {受講者が終わった時に決められること}
```

構成は5ブロック固定：**①原則 → ②なぜ着手前 → ③実際＝決め損ね → ④理想＝反実仮想 → ⑤演習**
（座学回は③④を「一般論の例示」に、ケース回は③④をChaptrの証拠で厚くする）

## S4.3 【ケース】monorepo→分離の代償を解剖する

- 証拠: `git show 01ef476 --stat`、`git show fa70572`、`git show bac6ff9`、`worklog/2026-06-03.md`
- ゴール: 「境界はコードでなくリポジトリで割る」を、分離の代償から理解して自分のIn/Outを引ける

### ① 原則（20秒）
🗗️ スライド「スコープ境界：In / Out / Later ——**特に Out を書く**」
🗣️ 「スコープを決めるとは、やることを並べることじゃない。**やらないことを書く**こと。そして境界が大きいときは、それをコードのフォルダでなく**リポジトリそのもの**で割る。これを守らなかった代償を見ます。」

### ② なぜ着手前か（30秒）
🗣️ 「スコープの膨張は、リポジトリ構成・依存・配布・名前、全部に波及します。境界を後で引き直すというのは、つまり**リポジトリを割り直す**こと。上流の意思決定の中でも、いちばん請求書が高い部類です。」

🎬 初期の構成を説明するスライド。
🗣️ 「Chaptrは最初、`media-scribe-workflow` という1つのリポジトリに、**CLIの配管ツール群・LaTeXレポート生成・GUI**を全部入れていました。monorepoです。当初は自然だった。」
🗣️ 「ところがGUIが育つにつれ、これは別物だと気づく。利用者も違う。配布形態も違う——CLIはpip、GUIはDMGやEXE。」

🗣️ 「そして分離の"下ごしらえ"を始めます。GUIリポジトリに持っていけない依存を先に切る。」
🎬 `git show 01ef476 --stat` を映す（巨大diff）。
🗣️ 「本番がこれ。`media_scribe_workflow/` を `chaptr/` へ。100ファイル超のリネーム、READMEは**276行削って69行**に。スコープを確定させるのに、これだけのコストを後から払った。」

### ③ さらに派生バグ（1分）

🗣️ 「しかも副作用があった。このリブランドで**再生ボタンのアイコンが消えた**。パス文字列は新しい場所に直したのに、アイコンの実ファイルが移行されていなかった。境界を引き直す作業は、こういう"移行漏れ"を必ず連れてきます。」
🖼️ スライド「代償：100+改名 ＋ README-207行 ＋ アイコン消失バグ」

### ④ 理想＝上流で決めていたら（1.5分）
🖼️ スライド「if：着手前にこう問えていたら」
🗣️ 「着手前にこう問えていたら防げた——『CLIとGUIは、同じ利用者が同じ入手経路で使うか？』。答えはノー。**なら最初から別リポジトリ**。」
🖼️ Before/Afterスライド：
- Before（実際）：1リポジトリに全部 → 5ヶ月後に分離 → 100+改名＋アイコン消失
- After（理想）：着手前に「GUIは別リポジトリ」と決定 → リブランドもアイコン消失も発生せず
🗣️ 「ポイントは2つ。**境界はコードのフォルダでなくリポジトリで割る**。そして、この判断は次の"名前"の章にも直結します——名前が3回揺れたのは、スコープが3回揺れていたからです。」

### ⑤ キャンバス演習（30秒）
✍️ 「あなたのプロジェクトのキャンバス③を開いて、In / Out / Later を各3つ書いてください。そして問う——**この中に、別リポジトリに分けるべき"別の利用者向け"の塊はないか？** あれば、いま線を引いておく。」

## S5.3 【ケース】曖昧な契約が生んだ1pxのバグ ★このコースの白眉
- 種別: ケース分析 / 目安: 6分 / キャンバス: ④中核データと契約
- 証拠: `worklog/2026-05-27.md`（全編）、`git show ea120d3`、`course/exercises/s7-duplicate-timestamp.txt`
- ゴール: 「不変条件を先に書く／契約は純粋関数1本に閉じる」を、実バグから骨身で理解する

### ① 原則（20秒）
🖼️ スライド「中核データの**不変条件**を、コードより先に文章で書く」
🗣️ 「アプリの背骨になるデータには、"守られるべき約束"があります。それを**不変条件**と呼びます。これを着手前に書いたか書かなかったかで、1ピクセルのバグが出るかどうかが決まる。実例で見せます。」

### ② なぜ着手前か（30秒）
🗣️ 「データの形は、UI・エクスポート・保存・テスト、**すべての経路が依存**します。契約が曖昧だと、経路ごとに解釈がずれる。そして"どの経路が正しいのか"を、バグが出てから初めて考えることになる。」

### ③ 実際＝決め損ね（2.5分）
🗣️ 「Chaptrには、章の名前を `--` で始めるとその区間をカットする機能があります。波形には赤い斜線が出る。ある日、ユーザーからこう報告が来ます。」
🎬 `worklog/2026-05-27.md` の該当箇所（ユーザー報告の引用）を映す。
🗣️ 「『`--`をつけても斜線が出ない。OKなものとダメなものがある』。」
🎬 演習データ `course/exercises/s7-duplicate-timestamp.txt` を開く。末尾をハイライト。
🗣️ 「原因はこれ。先頭に `0:00:00 --捨て`、そして**末尾にも `0:00:00 アンコール`**。同じ0:00:00が2つある。時刻順に並べると、除外区間が `0 → 0`、つまり**幅ゼロ**。斜線は1ピクセルも描かれない。」
🖼️ スライド「契約の穴：『同一時刻の章を許すか』を決めていなかった」
🗣️ 「誰も『同じ時刻の章が複数あったらどうするか』を決めていなかった。だから起きた。」

### ③ 二次災害：テストが本番を守れていなかった（1分）
🎬 worklog の「テストが本番ロジックをコピー再現していた」箇所を映す。
🗣️ 「さらに悪いことに。この区間計算のロジックが、**波形表示・エクスポート・テストの3箇所にコピー**されていた。テストは自分のコピーを検証していたので、本番にバグがあっても通ってしまう。契約を1箇所に閉じていなかった代償です。」

### ④ 理想＝上流で決めていたら（1.5分）
🖼️ スライド「if：着手前にこの不変条件を書いていたら」
```
中核データ：チャプター（時刻＋名前のリスト）
不変条件：
  - 章は時刻の昇順で扱う
  - 同一時刻の章は「起こりうる」
  - 除外区間は「厳密に大きい次の時刻」まで
  - 上記の計算は compute_excluded_regions() 唯一の実装とする
```
🗣️ 「着手前にこの4行を書いていれば、バグは生まれなかった。実際の修正も、結局**この形に作り直す**ことでした。」
🎬 `git show ea120d3` の該当関数を映す。
🗣️ 「波形・エクスポート・テストが、全部この1つの純粋関数を呼ぶ。これが『契約は純粋関数1本に閉じる』ということ。**後からたどり着いた正解を、上流で先取りする**——それが不変条件を先に書く、の意味です。」

### ⑤ キャンバス演習（30秒）
✍️ 「キャンバス④に、あなたのアプリの**中核データを1つ**、そしてその**不変条件を3つ**書いてください。特に『同時に起きたら？』『空だったら？』『順序は？』の3つの境界を問うと、契約の穴が見つかります。」

✂️ 編集メモ：worklogは全画面で"生の思考"を読ませる。特にユーザー報告の引用と原因特定の瞬間は等速。

## S7.3 【ケース】配布地獄15コミットを時系列で解剖
- 種別: ケース分析 / 目安: 6分 / キャンバス: ⑥配布制約（＋⑦技術選定）
- 証拠: CHANGELOG v2.1.29-34、`git log` の1/11-12、`git show f62a81c --stat`
- ゴール: 「配布は工程でなく制約」を理解し、地獄を"予期された作業"に変える発想を持つ

### ① 原則（20秒）
🖼️ スライド「配布は、あとでやる**工程**ではない。アーキテクチャを縛る**制約**だ。」
🗣️ 「多くの人が、機能を作ってから『さて配布するか』と考えます。順序が逆。配布先とその制約は、実装の方針を決める。後から足すと総取っ替えになる。その現場を時系列で見ます。」

### ② なぜ着手前か（30秒）
🗣️ 「『ffmpegに依存する』『ワンファイルEXEにしたい』『OSごとにブラウザのクッキー取得が違う』——これらは全部、**コードの書き方を規定する制約**です。制約を知らずに書いたコードは、配布段階で作り直しになる。」

### ③ 実際＝決め損ね（3分）
🗣️ 「Chaptrは配布を実装後に考え始めました。すると、たった2日でこれだけのことが連鎖します。」
🎬 CHANGELOG を v2.1.29 から順に映しながら、1行ずつ：
🖼️ スライド「配布地獄の連鎖（コミット順）」
```
① コンソール窓が一瞬光る        → --onefile を --onedir に         (cfc3278)
② でもワンファイルで配りたい      → PyInstaller から Nuitka へ乗換    (f62a81c)
③ Nuitkaでメモリ不足           → yt-dlp を外部exeに分離            (989f283)
④ CIが対話プロンプトで停止       → --assume-yes フラグ追加           (be7e6bb)
⑤ クッキー取得がOS依存          → Safari/Edge/Firefox 分岐          (3b7b98c)
⑥ macOS DMGが Resource busy    → sync+sleep 追加                  (a04954f)
```
🗣️ 「1つ直すと、次が出る。これがパッケージングの典型的な連鎖です。しかも④⑥は**CIでしか再現しない**。ローカルで動いても安心できない。」
🎬 `git show f62a81c --stat` を映す。
🗣️ 「注目してほしいのは、macOSはPyInstallerのまま、**Windowsだけ**Nuitkaに変えていること。全部を一気に乗り換えてはいない。ここは良い判断——次のS8で扱います。」

### ④ 理想＝上流で決めていたら（1.5分）
🖼️ スライド「if：着手前に配布キャンバスを1枚書いていたら」
```
⑥ 配布・運用制約
  誰が   : 自分＋同じ吹奏楽団のメンバー（非エンジニア）
  OS     : macOS(AppleSilicon/Intel) と Windows
  入手   : スタンドアロン配布（pip前提にしない）
  依存   : ffmpeg/ffprobe/yt-dlp は同梱（別途インストールを要求しない）
  パッケージャ: コンソール非表示のワンファイルが要る → 最初からNuitka前提
```
🗣️ 「これを着手前に書いていれば、Nuitka前提・依存同梱前提で最初から組めた。連鎖の大半は設計時に吸収できたはずです。」
🖼️ スライド（正直に）「ただし——全部は予見できない」
🗣️ 「ここで嘘はつきません。配布キャンバスを書いても、地獄が完全に消えるわけじゃない。CIでしか出ないエラーは、やってみないと分からない。でも目的はそこじゃない。**地獄を"予期された作業"に変える**こと。『配布は必ず揉める。だから時間を確保しておく』と分かっているだけで、慌てずに済む。」

### ⑤ キャンバス演習（20秒）
✍️ 「キャンバス⑥を書いてください。特に2つ——**依存を同梱するか要求するか**、そして**コンソール非表示など配布形態の要件**。この2つがパッケージャ選定を決めます。」

✂️ 編集メモ：連鎖スライドは①→⑥を順に出現させ、"積み上がる"感を出す。

## S9.1 片道ドアと両開きドア：メタ意思決定
- 種別: 座学 / 目安: 4分 / キャンバス: ⑧可逆性マップ
- 証拠: 2回の改名 vs アイコン/テーマ色の気軽な変更
- ゴール: どの決定を着手前に固め、どれは走りながら直してよいかを仕分けられる

### ① 原則（20秒）
🖼️ スライド「決定を2種類に分ける：**片道ドア** と **両開きドア**」
🗣️ 「上流設計の一番大事な技術は、実は『**全部を悩まない**』ことです。決定には2種類ある。取り消しに高くつく"片道ドア"と、すぐ戻せる"両開きドア"。片道だけ慎重に決めればいい。」

### ② なぜこれがメタ意思決定か（30秒）
🗣️ 「これはキャンバスの①〜⑩の"どれを先に決めるか"を仕分ける、決定についての決定です。これがないと、上流設計は『全部を完璧に決めるまで動けない』麻痺になる。」

### ③ 仕分けの基準（1.5分）
🖼️ スライド「3ヶ月後に変えると、何がドミノ倒しになるか？」
🗣️ 「見分け方は1つの問い——『これを3ヶ月後に変えたら、何が連鎖して壊れるか』。倒れる数が多いほど片道ドアです。」
🖼️ 2列スライド：
```
片道ドア（着手前に慎重に）      両開きドア（即決、後で直す）
- データ形式・ファイル契約        - UIレイアウト
- リポジトリ名 / 構成            - 配色・テーマ
- パッケージ名 / 公開API         - キーボードショートカット
- 配布チャネル                  - ログの文言
```

### ④ Chaptrの実際（1.5分）
🗣️ 「Chaptrは、この仕分けを**間違えた例と、正しくやった例の両方**を持っています。」

## スライドの作り方（共通ガイド）

### このコース特有の3スライド型
実装コースと違い、**証拠と反実仮想**が主役。多用する型：
1. **請求書スライド**（赤）：「決め損ね = ○○の代償」。数字を大きく（100+ファイル、15コミット、1px）。
2. **Before/Afterスライド**：❌実際（決め損ね）／✅理想（上流で決めていたら）の2カラム。全ケース章で使う。
3. **2列仕分けスライド**：片道/両開き、握る/委ねる、In/Out。意思決定の対比に。
4. **キャンバス記入例スライド**（📋）：Chaptr版の実記入を見せ、続けて受講者に空欄を促す。

### トーン&マナー
- Chaptrのテーマ色 **TokyoNight**（濃紺 + シアン/マゼンタ）で統一。
- 証拠（git/CHANGELOG/worklog）は**実物のスクショ**を使う。作り物でなく本物であることが、このコースの信頼性の源。
- 日本語フォントは Noto Sans JP。コードは等幅・大きめ。

### 収録前の準備チェックリスト（雛形）
```
□ 証拠を映すため、リポジトリを手元にclone（git show/log/CHANGELOG/worklog）
□ 該当コミットを事前に開いておく（本番で git show を打つなら打ち間違い対策でメモ）
□ キャンバスの空テンプレとChaptr記入例を用意（📋）
□ Before/Afterスライドの数字を再確認（100+, -207行, 15コミット 等は事実に忠実に）
□ worklogを映す回は、個人情報/絶対パスをマスク（cwdにフルパスが出る）
```
> ⚠️ worklog には作者のローカル絶対パス（`/Users/mashi/...`）が含まれる。**公開前にマスク**する。
