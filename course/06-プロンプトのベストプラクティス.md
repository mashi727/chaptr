# プロンプトのベストプラクティス（Claude Code 実践プレイブック）

> AIコーディング（Claude Code）を「なんとなく」から「戦力」にするための実践則。
> 抽象論を避け、**Chaptrの実際のセッション記録（`worklog/`）で裏の取れる型**だけを載せる。
> コースでは Section 10（AI協働）の中核教材＋ハンドアウトとして使う。

---

## 0. 前提となる考え方

**Claudeは「優秀だが記憶喪失の新メンバー」。**
毎セッション、プロジェクトの背景を知らない。だから良いプロンプトとは「賢い呪文」ではなく、
**必要な文脈・制約・事実を、過不足なく机に載せること**。

そして最重要の分業：
> **握る＝人間**（課題定義・境界・前提データの提示・最終判断）／ **委ねる＝AI**（調査・定型実装・リファクタ・テスト作成・選択肢の列挙）

---

## 1. 10の実践則（すべてChaptr証拠付き）

### 則1. 文脈は常設する — CLAUDE.md
毎回プロジェクトを説明し直さない。**概要・スコープ・決定事項・ディレクトリ**を書いた `CLAUDE.md` を置く。
- 📌 証拠：ChaptrはCLAUDE.mdを最初から持ち、思想・スコープ・「決定事項」を明記。これがClaudeの暴走（勝手な全面書き換え等）を防いだ。
- 🗣️ 効かせ方：迷ったときの判断基準（例「既存Zsh関数は維持、GUIのみPython」）を書くと、AIがその線で動く。

### 則2. 推測させる前に、事実（データ）を渡す
仮説で往復させるより、**生データを1つ見せる**方が速いことが多い。
- 📌 証拠（`worklog/2026-05-27.md`）：バグ調査でClaudeが `AskUserQuestion` で「①ダッシュ文字か②区間幅0か」と切り分けを質問。**ユーザーは答えず、実際の問題のチャプターファイルを渡した** → 見た瞬間に原因（同時刻の重複）が確定。
- 🗣️ 型：「（症状の説明）＋ 実際のデータ/ファイル/ログをそのまま貼る」。**まずデータの値を見る**。

### 則3. エラーは要約せず、そのまま貼る → 症状→仮説→対処のループ
「動かない」ではなく、**エラー全文**を貼り、原因の仮説→対処→次のエラー、を回す。
- 📌 証拠：配布地獄（CHANGELOG v2.1.29-34）は、この1コミット1修正のループの記録。コンソールちらつき→onedir→Nuitka→メモリ不足→…と1つずつ潰した。
- 🗣️ 型：「このエラーが出る：`<全文>`。原因の候補と、まず試す最小の対処を出して。」

### 則4. スコープと出力を制約する
「いい感じに」ではなく、**どこまで・どのファイル・どんな不変条件で**を明示。
- 📌 証拠：
  - 「まず**最小の変更で**試したい」（D&D修正、`c850e70`）
  - 「`export.py` と `export_split.py` の**両方**」（濁点NFC、`23edd5e`）
  - 「整形済みプロジェクトでは**出力不変**であることを確認」（区間計算、`ea120d3`）
- 🗣️ 型：「**この2ファイルだけ**を、**既存の出力を変えずに**直して。」

### 則5. 「動いた」で止めず、検証を指示に含める
最初の案で動いても、**エッジケースと検証**を人間が求める。
- 📌 証拠：worklogに残る検証コマンド群 — `pytest`（29 passed）、`git check-ignore`（追跡可能か）、`QIcon` の `null=False` 確認。
- 🗣️ 型：「直したら、`pytest tests/xxx` を通して結果を見せて。リサイズ後・連続操作も確認して。」

### 則6. 「効かない」ときは場所を疑わせる
直したのに反映されない → **実体はどのファイルか**を診断させる。
- 📌 証拠（`worklog/2026-05-27.md`）：`chaptr/ui/workers.py`(約127KB) と同名パッケージ `workers/` が共存し、Pythonはパッケージを優先。`workers.py`はデッドコードで、最初そこを編集していた。
- 🗣️ 型：「編集しても反映されない。**同名のモジュールとパッケージが競合していないか**、実際に import されている実体はどれか確認して。」

### 則7. 調査は委ねる — Explore / grep
「どこにあるか分からない」は自分で探さず**探索を委ねる**。
- 📌 証拠：アイコン消失調査で **Exploreエージェント**で読込箇所を特定、`git log --all -- '*play.png'` で「一度もコミットされていない」と判明（`bac6ff9`）。
- 🗣️ 型：「`<機能>` の実装箇所と、その参照元を洗い出して。関係ファイルを一覧で。」

### 則8. 判断は握る — 選択肢を出させて、自分が選ぶ
設計判断はAIに決めさせず、**選択肢と各トレードオフ**を出させてから人間が選ぶ。
- 📌 証拠：バグ修正で A（データ修正）/ B（コード恒久修正）を提示させ、ユーザーが **B** を選択。技術選定も PyInstaller継続 / Nuitka移行を比較して判断（`f62a81c`）。
- 🗣️ 型：「対処案を2〜3個、**それぞれの代償付き**で出して。決めるのは私。」

### 則9. ガードレールを指示する
- ✅ **作業ブランチで作業**（デフォルトブランチへ直コミットしない）。
  - 📌 証拠：「`main` ではなく作業ブランチにコミット」（`fix/excluded-region-zero-width`）。
- ✅ 破壊的操作・外部公開の前に**確認を求める**。
- 🗣️ 型：「作業ブランチを切ってからコミットして。main には直接触らないで。」

### 則10. セッションをまたぐ — worklogを書かせ、次に読ませる
1回で終わらない作業は、**判断ログ**で文脈を引き継ぐ。
- 📌 証拠：`worklog/2026-05-27.md` / `2026-06-03.md` が「決定と理由・未完了・地雷（デッドコード）・引き継ぎヒント」を残し、次セッションの起点になった。
- 🗣️ 型：終わりに「今日の**決定と理由・未完了・触ったファイル・次の地雷**をworklogに残して」。次回頭で「`worklog/最新.md` を読んでから続けて」。

## 2. 弱いプロンプト → 強いプロンプト（対比表）

| 場面 | ❌ 弱い | ✅ 強い |
|---|---|---|
| バグ報告 | 「斜線が出ないんだけど直して」 | 「先頭に`--`を付けても斜線が出ない。**このチャプターファイルを見て**（実データ添付）。OKなものとダメなものがある。」 |
| エラー対応 | 「ビルドが動かない」 | 「Windowsビルドでこのエラー：`<全文>`。原因候補と、まず試す最小の対処を。」 |
| 実装依頼 | 「ショートカット足して」 | 「`Home`キーで先頭チャプターへジャンプ。`keyPressEvent` 周辺、**最小の変更**で。」 |
| リファクタ | 「いい感じに整理して」 | 「区間計算が3箇所にコピーされている。**GUI非依存の純粋関数1本**に集約して、波形・エクスポート・テストが同じものを呼ぶ形に。**出力は不変**で。」 |
| 技術選定 | 「Nuitkaにして」 | 「コンソール非表示のワンファイルが要る。PyInstaller継続とNuitka移行を**代償付き**で比較して。決めるのは私。」 |
| 仕上げ | 「これで完成でいい？」 | 「`pytest` を通して結果を見せて。既存の失敗と新規の失敗を区別して。」 |

**共通の差**：強い方は必ず「**事実（データ/エラー全文）＋ 制約（範囲/不変条件）＋ 分業（決めるのは私）**」を含む。

## 3. プロンプトの型（コピペ用テンプレ）

### 調査
```
<機能/症状> の実装箇所と参照元を洗い出して。
実際に実行されている実体はどれか（同名の重複がないか）も確認して。一覧で。
```

### バグ（データ先出し）
```
<症状の一文>。再現する実データを貼る：
<データ/ファイル/ログをそのまま>
まず原因の候補を出して。推測の前にこのデータの値を見て。
```

### 実装（範囲と不変条件を固定）
```
<やること>。
対象は <このファイルだけ>。既存の <出力/挙動> は変えないで。
できたら <検証コマンド> を通して結果を見せて。
```

### 設計判断（握る）
```
<課題>。対処案を2〜3個、それぞれの代償付きで。
まだコードは書かないで。決めるのは私。
```

### 引き継ぎ（セッション末）
```
今日の「決定と理由 / 未完了・宿題 / 触ったファイル / 次の地雷」を
worklog に残して。次のセッションが読めば続きから動ける形で。
```

## 4. アンチパターン（AIコーディングでやりがち）

| アンチパターン | なぜ悪い | 直し方 |
|---|---|---|
| 「いい感じにして」 | 制約がなく暴走・的外れ | 則4：範囲と不変条件を固定 |
| エラーを貼らず「動かない」 | 仮説が立てられない | 則3：全文を貼る |
| 症状を言葉で説明し続ける | 往復が増える | 則2：実データを渡す |
| 「動いた」で即マージ | エッジケース・回帰を見逃す | 則5：検証を指示 |
| 全部一気に「リファクタして」 | 巨大diff・物語が潰れる | 小さく・可逆に（則8で分割相談） |
| 設計判断をAIに丸投げ | 責任と文脈が失われる | 則8：選択肢を出させ人間が選ぶ |
| 毎回プロジェクトを説明 | 無駄・ぶれる | 則1：CLAUDE.mdに常設 |
| 記録を残さず次セッション | 同じ議論・地雷を踏み直す | 則10：worklog |

## 5. 30秒チェック（プロンプトを送る前に）

1. **事実**を渡したか？（データ／エラー全文／該当ファイル）
2. **制約**を書いたか？（範囲・不変条件・「最小の変更で」）
3. **分業**を示したか？（決めるのは私／選択肢を出して）
4. **検証**を求めたか？（pytest・再現確認）
5. これは**CLAUDE.mdに書くべき常設文脈**ではないか？

3つ以上Noなら、送る前に一言足す。それだけで往復が半分になる。
