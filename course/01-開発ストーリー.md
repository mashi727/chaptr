> Udemyコースの「背骨」になるドキュメント。
> git履歴（全52コミット）・`CHANGELOG.md`・`worklog/` から復元した、Claude Code を使った実際の開発過程を時系列でまとめたもの。
> ナレーション台本（`course/03`）とカリキュラム（`course/02`）はここを元に組み立てる。

## ⚠️ 資料の出典と限界（重要）

この物語の**出典はフェーズによって違う**。教材化・収録の前提が変わるので先に明記する。

| 出典 | 対象 | 何が復元できるか |
|---|---|---|
| git履歴 + CHANGELOG | **全フェーズ（0〜5）** | 何を・いつ・どの順で作ったか（コミット単位の事実） |
| `worklog/` の詳細セッション記録 | **フェーズ5のみ（2026-05-27以降）** | 使ったプロンプト・モデル・所要時間・試行錯誤・ハマった点まで |

- **worklog が実在するのは 2 本だけ**：`worklog/2026-05-27.md`（除外ハッチング修正）と `worklog/2026-06-03.md`（アイコン復旧）。両方フェーズ5。worklog習慣自体がこの時期に始まり、リポジトリに入ったのも `f2cf8eb`（2026-06-03）から。
- **開発当初〜中盤（フェーズ1 MVP・2 配布・3 リファクタ・4 リブランド）には worklog が無い**。当時のClaudeとのやり取りの生ログは残っていない。
- 収録上の含意：
  - フェーズ5（Section 7・一部8）＝**過去セッションの追体験**が可能（worklogが台本の裏付けになる）。
  - フェーズ0〜4（Section 1〜6・8の大半）＝生ログが無いので、**収録時にタグをcheckoutして"再演"する**（当時と同じ作業をその場でClaudeとやり直して撮る）方式になる。台本の💬プロンプトは「当時こう指示したはず」という再構成であり、逐語ログではない。

## この物語が教材として強い理由

一般的な「Claude Code入門」動画は、**ゼロから綺麗なアプリを一気に作る**ものが多い。
だが Chaptr の履歴に残っているのは、もっとリアルな開発だ：

- MVPを1日で爆走で作る
- **配布(パッケージング)の壁**に2週間ぶつかる
- アーキテクチャを大きくリファクタして着地させる
- リポジトリを2回リブランドする
- 実際に使って初めて出るバグ（濁点の分離、重複タイムスタンプ、リブランド時の移行漏れ）を潰す

つまり「動くものを作る」から「配れて・保守できるものにする」までの**全工程**が残っている。
これは受講者にとって「自分もこの壁にぶつかるだろう」という共感ポイントになり、コースの価値になる。

## フェーズ0：前史 — 「配管ツール」という思想（2025-11）

Chaptrはいきなりデスクトップアプリとして生まれたわけではない。
出発点は **CLIツール群**だった（`CHANGELOG.md` の v1.0.0）。

- `rehearsal-download`：YouTube動画DL + Whisper文字起こし起動
- `tex2chapters`：LaTeXからチャプター抽出
- `/rehearsal`：Claude Code統合（SRT分析 + LaTeX生成）

思想は `CLAUDE.md` にある通り **「Gitの陶器と配管」**：単一目的のツールを組み合わせてワークフローを作る。
リハーサル動画 → 字幕(SRT) → タイムスタンプ付きレポートPDF、という自分の実需要から出発している。

**教材ポイント：**
- 「作りたいアプリ」ではなく「自分の困りごと」から始まっている。これがコース全体の背骨になる良い出発点。
- CLAUDE.md に思想・スコープ・ディレクトリ構成を先に書いている＝**Claude Codeに文脈を与える設計**。ここを最初のレクチャーで見せる。

CHANGELOGの開発ログによれば、12/26〜27で `prep_gui.py`（後のchaptr）が一気に立ち上がる：

- YouTubeチャプターのコピー＆ペースト連携

## フェーズ2：配布の壁 — 「動く」と「配れる」は別物（2026-01-05〜12）

ここがコースの**山場のひとつ**。動くアプリを他人のマシンで動かすための格闘が15コミット続く。

### 2-1. macOS：デュアルアーキ + ffmpeg同梱（1/6）
```
039bf62 Add dual macOS architecture builds and bundle ffmpeg/ffprobe
```
`.github/workflows/release.yml` に +81行。Apple Silicon / Intel両対応、ffmpeg/ffprobeをバンドル。
「ユーザーにffmpegを別途入れさせない」ための地味だが重要な作業。

### 2-2. リポジトリのリネーム（1/10）
```
04da0b0 Rename repository and package to media-scribe-workflow
```
`rehearsal-workflow` → `media-scribe-workflow`。パッケージ名も一括変更。1回目のリブランド。

### 2-3. Manager層リファクタ + vce-split CLI（1/10〜11）
```
b2ee3a4 Add vce-split CLI for chapter-based video splitting
d27bbef Refactor SourceFileManager and add comprehensive documentation
81a3879 Release v2.1.28: Manager refactoring and vce-split CLI
```
CHANGELOG v2.1.28 によれば PlaybackManager / ChapterManager / ExportOrchestrator / SourceFileManager を導入し、肥大化した `MainWorkspace` を分割し始める。

### 2-4. Windowsビルド地獄（1/11〜12）
CHANGELOGの v2.1.29〜2.1.34 がこの数日に凝縮：
```
3b7b98c Fix YouTube download cookies for cross-platform support   # Safari/Edge/Firefox
cfc3278 Fix Windows console window flash on startup               # onefile→onedir
f62a81c Switch Windows build to Nuitka for clean onefile EXE      # PyInstaller→Nuitka
989f283 Fix Windows Nuitka build by externalizing yt-dlp          # メモリ不足→yt-dlp.exe分離
be7e6bb Add --assume-yes-for-downloads flag for Nuitka CI build   # CIで対話プロンプト詰まり
a04954f Fix macOS DMG creation Resource busy error                # sync+sleep
```

これは**「1つ直すと次が出る」パッケージングの典型的な連鎖**。
コンソールがちらつく → onedirに → でもワンファイルにしたい → Nuitkaへ → メモリ不足 → yt-dlpを外部exeに分離 → CIが対話プロンプトで止まる → 自動承認フラグ…と、実際のトラブルシュートが1コミット1つずつ記録されている。

**教材ポイント：**
- **これぞ「Claude Codeが最も光る場面」**。エラーメッセージを貼る → 原因の仮説 → 対処 → 次のエラー、のループ。
- 「なぜPyInstallerからNuitkaへ移ったか」のような**技術選定の判断**を、コミットとCHANGELOGから追える。
- CI（GitHub Actions）でしか再現しないエラー（`--assume-yes-for-downloads`）は、ローカルでは気づけない学び。

## フェーズ5：実戦投入と磨き込み（2026-05-27〜06-29）

ここは `worklog/` に**生の開発セッション記録が残っている**、教材的に最も価値の高いパート。
Claude Codeの実際の使い方（Explore、AskUserQuestion、grep、デッドコード発見）が全部見える。

### 5-1. 除外ハッチングが出ないバグ（5/27, `ea120d3`）— worklog あり
**症状**：チャプター冒頭に `--` を付けても波形に斜線（除外区間）が出ない。「OKなものとダメなものがある」。

**Claude Codeでの解き方（worklog/2026-05-27.md より）：**
1. `grep` で斜線描画箇所を特定
2. `--` 判定の全使用箇所を確認（表示・エクスポート・保存すべてASCII厳密判定）
3. 2つの仮説を提示（①ダッシュ文字の取り違え、②区間幅0）
4. **AskUserQuestionで切り分けようとしたらユーザーが拒否 → 代わりに実データを提示**
5. 実チャプターファイルを精査 → **末尾に `0:00:00.000 ヴォカリーズ` が先頭 `--捨て` と同時刻で衝突**、区間幅0で1pxも描かれないと特定
6. 区間計算を純粋関数 `models.compute_excluded_regions()` に集約（波形・エクスポート・テストで共有）
7. **重大発見**：`chaptr/ui/workers.py`(約127KB) は同名パッケージ `workers/` に隠蔽された**デッドコード**。最初そこを編集してしまい revert
8. 回帰テスト2件追加、波形テスト29 passed でコミット

**教材ポイント（宝の山）：**
- 「**まずデータの値を見る**」— AskUserQuestionより実データが早いことがある
- テストが**production ロジックをコピー再現**していて本番バグを検知できなかった構造的欠陥 → 純粋関数に切り出して共有（フェーズ3のテストの伏線回収）
- **デッドコードの罠**：`workers.py` と `workers/` が共存しPythonはパッケージを優先。「編集したのに効かない」時の切り分け方
- 使用モデル：Opus 4.7 (1M context)、所要**約60分**（worklogに記録）

### 5-2. アイコン消失（6/3, `bac6ff9`）— worklog あり
**症状**：再生ボタンのアイコンが消えた。

**原因**：フェーズ4のリブランド `01ef476` で、パス文字列は `chaptr/ui/icons/` に更新されたが、**実ファイルが移行されていなかった**。さらに `.gitignore` の `*.png` 全除外で、そもそもアイコンは一度もコミットされていなかった。

**解き方（worklog/2026-06-03.md より）：**
1. Explore エージェントでアイコン読込箇所を特定
2. `git log --all -- '*play.png'` → 過去一度もコミットされていないと判明
3. ディスク全体検索で派生元 `movie-viewer` に同名アイコンを発見（Chaptrはmovie-viewer派生）
4. コピー + `.gitignore` に `!chaptr/ui/icons/*.png` の例外を追加
5. `git check-ignore` で追跡可能を確認、`QIcon` が `null=False` でロードされることを検証

**教材ポイント：**
- **リブランド/移行で「参照は直ったが実体が来ていない」**のは定番事故。`git log --all -- <file>` で追跡履歴を確認する技
- `.gitignore` のワイルドカード除外がアセットを飲み込む罠と、`!` 例外の使い方
- 使用モデル：Opus 4.8 (1M context)、所要**約15分**

### 5-3. その後の磨き込み（6/8〜6/29）
```
e79b7c7 Unify chapter title font to bundled Noto Sans JP Bold   # フォント同梱で環境非依存
0e4e670 Fix Windows-breaking issues in export/download pipeline # Windows実戦バグ
2693315 Bundle yt-dlp module in Windows build for playlist parity
800c6f5 Merge pull request #1                                    # 初のPRマージ
2f1955d Add per-chapter video rotation (preview + burn-in), 2.2.0 # 機能追加 +262行
6c195ce Speed up merged export: per-segment fast-seek inputs      # 性能改善（trim→fast-seek）
23edd5e Fix detached dakuten in burned-in titles (NFC-normalize)  # 濁点分離をNFC正規化
```

特に `23edd5e` の**濁点分離バグ**は日本語アプリならではの学び：焼き込みタイトルの「が」「ぱ」等の濁点/半濁点が分離文字（NFD）になって崩れる → `unicodedata.normalize("NFC", ...)` で解決。
`6c195ce` は**性能改善**：全体をtrimしてからconcatする方式を、セグメントごとにfast-seek入力する方式に変えて書き出しを高速化。

**教材ポイント：**
- 実際に自分のリハーサル動画で使うから出てくるバグ（濁点、インターレース、重複タイムスタンプ）。**ドッグフーディングの価値**。
- `CLAUDE.md` の「将来の検討事項」にある **mpv統合によるインターレース対応** は、「まだ解いていない課題」として提示でき、コースの締めに「あなたならどう解く？」の宿題にできる。
