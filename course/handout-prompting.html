プロンプトのベストプラクティス · Prompting Playbook

握るは人間、委ねるはAI。
良いプロンプトは呪文でなく事実の提示。

Claude Codeは「優秀だが記憶喪失の新メンバー」。強いプロンプトはいつも 事実 ＋ 制約 ＋ 分業 を含む。以下はすべて Chaptr の実セッション記録（worklog）で裏が取れる型。

事実（データ/エラー全文）＋ 制約（範囲/不変条件）＋ 分業（決めるのは私）
01弱いプロンプト → 強いプロンプト左の赤を、右の緑に書き換える
CASE 1バグ報告
✕ 弱い「斜線が出ないんだけど直して」
✓ 強い「先頭に -- を付けても斜線が出ない。このチャプターファイルを見て（実データ添付）。OKなものとダメなものがある。」
CASE 2エラー対応
✕ 弱い「ビルドが動かない」
✓ 強い「Windowsビルドでこのエラー：<全文>。原因候補と、まず試す最小の対処を。」
CASE 3実装依頼
✕ 弱い「ショートカット足して」
✓ 強い「Homeキーで先頭チャプターへジャンプ。keyPressEvent 周辺、最小の変更で。」
CASE 4リファクタ
✕ 弱い「いい感じに整理して」
✓ 強い「区間計算が3箇所にコピーされている。GUI非依存の純粋関数1本に集約し、波形・エクスポート・テストが同じものを呼ぶ形に。出力は不変で。」
CASE 5技術選定
✕ 弱い「Nuitkaにして」
✓ 強い「コンソール非表示のワンファイルが要る。PyInstaller継続とNuitka移行を代償付きで比較して。決めるのは私。」
CASE 6仕上げ
✕ 弱い「これで完成でいい？」
✓ 強い「pytest を通して結果を見せて。既存の失敗と新規の失敗を区別して。」
0210の実践則すべてworklog証拠付き
1文脈は常設する — CLAUDE.md に概要・スコープ・決定事項
2推測させる前に、事実（データ）を渡す — まずデータの値を見る
3エラーは要約せず全文を貼る — 症状→仮説→対処のループ
4スコープと出力を制約 — このファイルだけ／出力不変で
5「動いた」で止めず検証を指示 — pytest・再現確認
6効かない時は場所を疑わせる — 実体はどれか（デッドコード）
7調査は委ねる — Explore／grep で洗い出し
8判断は握る — 選択肢を代償付きで出させ、自分が選ぶ
9ガードレールを指示 — 作業ブランチ／main直コミット禁止
10セッションをまたぐ — worklog に決定・理由・地雷を残す

0430秒チェック送信ボタンを押す前に
  1. 事実を渡したか？（データ／エラー全文／該当ファイル）
  2. 制約を書いたか？（範囲・不変条件・「最小の変更で」）
  3. 分業を示したか？（決めるのは私／選択肢を出して）
  4. 検証を求めたか？（pytest・再現確認）
  5. これは CLAUDE.md に書くべき常設文脈ではないか？

3つ以上Noなら、送る前に一言足す。それだけで往復が半分になる。
